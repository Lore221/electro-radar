# CBC: аналитическое наведение по фактическому collision sweep

Исследование ветки develop, обновлено 2026-10-31. Независимый вариант коллеги — в newcore,
в файле с тем же путём. Вариант коллеги при подготовке этого документа не читался.

**Контракт ядра:** найти pitch/yaw для заданной неподвижной в рамках одного запроса
точки X=(x1,y1,z1). Вычисление самой точки упреждения — отдельный слой. Скорость,
ускорение и UUID цели основному решателю точки не нужны. **Текущее расширение:**
связать ядро с прогнозом, временем наведения и выстрела, определить отказы и проверить
полный расчёт на движущихся целях. Это расширение выполнено в исследовательской модели.

**Алгоритм точки — раздел 13, упреждение — 14, задержки и полный цикл — 16–20.**
Сначала решается точное квадратное
уравнение для прежнего sweep CBC и ограниченного числа его соседей. Если это
не помогло, выполняется поиск по тангенсу pitch с доказанной вогнутостью вспомогательной
функции и аналитической границей её расхождения с CBC. Плохо обусловленное обратное

а не безусловным «сущность недостижима».

## 2. Обозначения и точная прямая формула

Положение — блоки, скорость — блоки/тик, ускорение — блоки/тик².

- C — мировой центр вращения неподвижной установки.
- u — единичный вектор оси выстрела.
- s>0 — начальная скорость центрального выстрела.
- L — осевое расстояние от C до spawn, с учётом сдвига CBC.
- g≥0 — величина ускорения вниз; G=(0,-g,0).
- k=min(projectile.drag × density,1), q=1-k.
- n — целое число завершённых шагов до текущей проверки столкновения; первый sweep имеет n=0.

В CBC getGravity возвращает знаковый компонент, который getForces добавляет
непосредственно. Адаптер получает G из фактической логики; нельзя повторно менять
знак, терять isNoGravity или использовать только базовый параметр из JSON.

При обычной нормализации скорости:

~~~
v_(n+1) = q v_n + G
p_(n+1) = p_n + (1-k/2)v_n + G/2

S_n = (1-q^n)/k
A_n = (1-k/2) S_n
B_n = (n-A_n)/k

v_n = q^n v_0 + S_n G
p_n = p_0 + A_n v_0 + B_n G
~~~

Вывод: первое уравнение суммируется геометрическим рядом. Подстановка его решения
в сумму приращений p даёт коэффициенты A и B. Поэтому формула точна в вещественной
арифметике в целых n и вычисляется за O(1), независимо от числа прошедших шагов.

Ветви:

~~~
k=0: A_n=S_n=n, B_n=n²/2, v_n=v_0+nG.
n=0: A_n=B_n=S_n=0.
k=1, n≥1: A_n=1/2, B_n=n-1/2, S_n=1, v_n=G.
~~~

При k=1 выражение q^0 в n=0 обрабатывается как 1, а log(q) не вычисляется.

Ограничение: Vec3.normalize возвращает ZERO при |v|<1e-4. В этой области CBC
перестаёт применять drag, и приведённая линейная рекурсия меняется. Необходимо
аналитически проверить применимость модели на всей предшествующей траектории.

Для выбранного направления при 0<k<1 скорость имеет вид:

~~~
v_j = z v_0 + (1-z)G/k, z=q^j
|v_j|² — квадратный многочлен по z.
~~~

Его минимум на диапазоне j=0..n находится по концам и вершине. Для точного минимума
по целым j достаточно проверить также соседние целые j около log(z_vertex)/log(q).
Это фиксированное число аналитических проверок, без цикла по j.
Если минимум может попасть в область изменённой нормализации, нельзя выдавать
точное решение этой модели: требуется отдельная ветвь или UNSUPPORTED_MODEL.

Аналогично проверяется |v_(n+1)|≥0.01 для выбранного sweep, иначе CBC не выполнит
обычную проверку попадания. Для полной классификации тиков удобно сначала доказать
эти ограничения для всего диапазона разрешённых углов и горизонта:
минимум скорости по углам достигается при максимальном допустимом u_y.
Это снова квадратная функция z. Если общего доказательства нет, результат поиска
не превращается автоматически в доказательство отсутствия решений для реального CBC.

## 3. Геометрия запуска и время цели

В идеальной осевой геометрии:

~~~
p_0 = C + L u
v_0 = s u
R_n = L+s A_n
U_n = s q^(n+1)
V_n = S_(n+1)
~~~

Create вращает локальные векторы относительно центра блока ZERO, затем добавляет
anchor. Поэтому при неподвижном anchor C не меняется с углом, а осевой offset L
можно включить в формулу. Это устраняет внешний цикл «изменить угол — пересчитать
дуло — снова решить». Погрешность реальных float/LUT-преобразований проверяется
в финальной стадии, а не объявляется нулевой.

Цель задаётся квадратным полиномом X(t)=P+Vt+a t²/2. Для статики V=a=0,
для постоянной скорости a=0. Все три случая используют одну функцию перехвата.
Если sample старше запуска на tau=age+delay+phase, сначала за O(1) вычисляются
P_launch=P+V tau+a tau²/2 и V_launch=V+a tau; затем t отсчитывается от запуска.
age относится к серверному sample; delay — к запланированному выстрелу;
phase согласует момент target bbox с порядком entity ticks.

Разность соседних скоростей определяет a, но сама по себе не определяет порядок
обновления координаты. Для дискретного движения с постоянным ускорением:

~~~
X_n = P+v n+a n(n+eta)/2
eta=-1: сначала перемещение старой скоростью, затем обновление скорости;
eta= 0: половинный вклад ускорения в координату;
eta=+1: сначала обновление скорости, затем перемещение новой скоростью.
~~~

Это тот же квадратный полином, если линейным коэффициентом взять V=v+eta a/2.
Ядро принимает коэффициенты полинома и не предполагает, что для любой сущности
подходит одна и та же фаза. Получение UUID/скоростей не проектируется, но это
математическое соглашение обязательно для точного упреждения.

CBC читает bbox сущности при обработке текущего тика. Параметр f ниже — доля
геометрического отрезка, а не команда дополнительно передвинуть цель на W f.
Модель X(n+f) допустима только как отдельно выбранная интерполяционная модель,
а не как буквальное воспроизведение текущего clipAndDamage.

Для lifetime T>0 у обычной автопушки sweep допускается в n=0..T-1:
родительская физика выполняется до уменьшения ageRemaining. Дополнительный тик
задержки выстрела, если он нужен, задаётся через delay, а не прибавлением к времени
полёта. Особые снаряды/фузеи могут ограничивать этот горизонт раньше.
У больших пушек без lifetime нужен явный конечный горизонт задачи; константа 600
сама по себе не является физическим пределом CBC.

## 4. Попадание в выбранном тике решается квадратным уравнением

В свободном полёте настоящий исходный отрезок CBC:

~~~
H_n(f) = p_n + f v_(n+1), 0≤f≤1
       = C + (R_n+f U_n)u + (B_n+f V_n)G.
~~~

Пусть (dx,h,dz)=X_n-C, r²=dx²+dz², Y=h+g B_n.
Устранение единичного направления даёт:

~~~
r² + (Y+f g V_n)² = (R_n+f U_n)²

a f² + b f + c = 0
a = (g V_n)²-U_n²
b = 2(g V_n Y-R_n U_n)
c = r²+Y²-R_n².
~~~

Это точная обратная задача для точки и выбранного sweep в принятой модели.
Ньютона по pitch внутри этого тика не требуется.

Для каждого допустимого корня f:

~~~
u = (dx, Y+f g V_n, dz) / (R_n+f U_n)
theta = atan2(u_y, sqrt(u_x²+u_z²))
yaw   = atan2(-u_x,u_z)
~~~

theta — физическое возвышение; yaw — соглашение Minecraft.
Корни f вне [0,1], недопустимые углы и некорректные направления отбрасываются.
L и знаменатель нельзя молча заменять модулем. Нулевой знаменатель обрабатывается
как отдельная геометрическая вырожденность, а не делением на малое число.

Квадратное уравнение решается устойчиво:

~~~
D = b²-4ac
Q = -0.5 (b+copysign(sqrt(D),b))
f1=Q/a, f2=c/Q.
~~~

Нужны отдельные ветви линейного уравнения, кратного корня, Q=0 и тождественного
уравнения. Малый коэффициент определяется относительно масштаба и погрешности,
а не одним произвольным абсолютным epsilon. При неопределённом знаке D применяется
повышенная точность/интервальная оценка либо возвращается UNRESOLVED, а не NO_SOLUTION.

Таким образом, после выбора n остаются несколько операций, один sqrt и
восстановление направления. Оба угла получаются совместно; для движущейся цели
yaw ориентируется на X_n, а не на её текущую позицию.

## 5. Ранее исследованный поиск по времени и резервные методы

Текущий поиск для заданной точки описан в разделе 13. Ниже сохранены формулы
для поиска по времени, который нужен также как резерв при плохой обусловленности
обратного поиска по углу. В статическом контракте V=a=0. Совместное решение
упреждения не является требованием к основному решателю точки.

### 5.1 Основная функция перехвата: статика, скорость, ускорение

Подставляем полином движения цели в аналитическую формулу снаряда и устраняем u:

~~~
D(t) = P+Vt+a t²/2-C-B(t)G
R(t) = L+s A(t)
F(t) = D(t)·D(t)-R(t)² = 0
~~~

Упреждение входит непосредственно в F. Внешнего цикла «предсказать точку —
решить статическую задачу — заново предсказать точку» нет.

Для решения используются аналитические производные:

~~~
D'  = V+a t-B'G                  D'' = a-B''G
R'  = s A'                       R'' = s A''
F'  = 2[D·D'-R R']
F'' = 2[D'·D'+D·D''-(R')²-R R'']

lambda=log(1-k), z=exp(lambda t), c_step=1-k/2
A'  = -c_step lambda z/k         A'' = lambda A'
B'  = (1-A')/k                   B'' = -A''/k
~~~

Одна оценка F/F'/F'' делит ОДНО значение z. Ускорение добавляет несколько умножений
и сложений трёхмерных векторов, но не добавляет ни потикового цикла, ни отдельного
решателя. log(1-k) и параметры профиля кешируются.

Первый шаг нового измерения может использовать A/B и производные, сохранённые
для предыдущего t: изменились P/V/a, а баллистические коэффициенты в этой точке
те же. Такая первая оценка не требует нового exp. Это кеш коэффициентов, а не
разрешение использовать старую точку прицеливания при движении цели.
Кеш действителен при неизменном профиле снаряда; изменения позы/геометрии установки,
цели и выбранной ветви также учитываются при проверке пригодности прошлого решения.

При изменяющемся ускорении обозначим входы очередного расчёта индексом j:

~~~
X_j(t) = P_j + V_j t + a_j t²/2
F_j(t) = |X_j(t)-C-B(t)G|² - [L+s A(t)]².
~~~

Индекс j обозначает новый запрос, t — прогнозируемое время после нового запуска.
Последовательность a_j может меняться плавно, скачком или вместе с направлением V_j.
Это не добавляет неизвестных в F_j и не увеличивает стоимость одной её оценки.
Меняется расстояние до прежнего корня, а значит, число уточнений и вероятность
полного поиска. Прошлый корень — только начальное приближение для свежего F_j.
Нельзя считать его решением по новому снимку или автоматически вычитать из него
один тик: новый выстрел начинается заново из пушки.

Скачок входов не требует безусловно отбрасывать приближение: сначала дёшево
проверяются свежая невязка, обусловленность и допустимость шага в выбранной ветви.
При успешной проверке сопровождение продолжается. При неуспехе действует бюджет
восстановления, без незаметного перехода между LOW/HIGH. Сложный сценарий может
потребовать больше работы, даже если формула на каждом запросе осталась прежней.

Для продолжения корня:

~~~
Newton: delta = F/F'
Halley: delta = 2 F F' / [2(F')²-F F'']
t_new = t-delta.
~~~

Halley использует ту же экспоненту и локально имеет более высокий порядок
сходимости. При ненадёжном знаменателе, слишком большом шаге, выходе из интервала
ветви или росте ошибки используется защищённый Newton/бисекция либо возвращается
UNRESOLVED. Фиксированное малое число шагов не является доказательством сходимости.
Остановка задаётся пространственной ошибкой и запасом hitbox, не требованием
уточнять t до 1e-25. Около касания нужен отдельный разбор экстремума F.

t — корень гладкого продолжения, а не точное время реального collision sweep.
Полученный кандидат обязательно переводится в соседние целые n и уточняется
по разделу 4 и ближайшей допустимой точке из раздела 6. Успех Ньютон/Halley сам
по себе не разрешает выстрел.

### 5.2 Две ветви и полный захват корней основной функции

Ниже сохранено первоначальное правило глобального выбора по pitch. Для текущей
связки раздел 14.5 уточняет контракт: LOW/HIGH относятся к баллистической семье
для точки кандидата, а поддержание уже найденного перехвата не обещает каждый тик
находить глобальный минимум времени или pitch среди всех будущих перехватов.

Для большой пушки выдаются LOW и HIGH. На статической цели это привычные
меньшее и большее возвышение. Каждая ветвь имеет собственные t, направление,
прогноз точки цели и состояние сходимости. HIGH не должен молча заменяться LOW,
если навесное решение вышло за реальные ограничения CBC.

При постоянном ускорении нельзя математически предполагать ровно два решения.
Даже при k=0 F является многочленом четвёртой степени и может иметь четыре
положительных корня. Для 0<k<1 с квадратным движением цели:

~~~
F(t)=P4(t)+P2(t) exp(lambda t)+P0 exp(2 lambda t).
~~~

Индекс P обозначает максимальную степень полинома. Размерность этой системы 9,
поэтому ненулевая F имеет не более 8 действительных нулей с кратностями.
В обычной ситуации остаются две допустимые ветви, но общий захват должен уметь
найти остальные, проверить CBC-sweep и ограничения углов, затем выбрать
канонические LOW/HIGH по меньшему/большему физическому возвышению. Это правило
выбора двух пользовательских режимов, а не утверждение, что иных корней нет.

Полный захват сначала работает с ОДНОЙ этой функцией и её цепочкой производных,
не с восемью семействами событий. Между корнями нормализованной производной
функция монотонна; уточняются смены знака и проверяются сами критические точки.
При k=0 используются корни полинома степени ≤4. Затем каждый корень проверяется
по настоящему sweep. Несколько соседних тиков одной ветви не считаются разными
траекториями.

Во время сопровождения продолжается выбранная корневая ветвь. Неактивную можно
обновлять по запросу переключения, при котором её пригодность проверяется заново;
если нужны оба свежих результата, продолжаются обе ветви. При слиянии, исчезновении,
выходе за углы или неопределённости требуется повторный захват; случайно перескочить
Ньютоном с HIGH на LOW и сохранить прежнюю метку нельзя. На сложном ускоренном
движении сохранённая ветвь не считается доказанным глобальным минимумом pitch
без обновления остальных корней и повторной классификации.

Поиск корней F не доказывает полноту попаданий по дискретным отрезкам и объёмному
hitbox. Он даёт дешёвые кандидаты. Для редких пограничных случаев остаётся резерв
ниже; при исчерпании бюджета результат неизвестен, а не «попадание невозможно».

### 5.3 Резервный полный поиск через аналитические события

Для полного разбора дискретной точечной модели можно искать изменение существования
корней f в [0,1]. Это более дорогой резерв, не обычный путь захвата/сопровождения.

Продлим коэффициенты a(n), b(n), c(n) аналитически на вещественный n.
Это вспомогательная параметризация семейства отрезков; она не объявляется реальной
непрерывной траекторией CBC. Изменение числа допустимых корней происходит, когда:

1. Корень входит через f=0: c(n)=0.
2. Корень выходит через f=1: a(n)+b(n)+c(n)=0.
3. Корни сливаются: D(n)=b²-4ac=0.
4. Уравнение меняет степень: a(n)=0; для вырожденностей учитывается и b(n)=0.
5. Направление пересекает границу разрешённого pitch.
6. r²(n)=0: вертикальный случай, где yaw теряет определённость.

Для границы pitch=theta_0 введём K=g V_n R_n-U_n Y.
Устранение f даёт дополнительную функцию события:

~~~
E_theta(n) =
  r²(n) [g V_n-U_n sin(theta_0)]²
  - K(n)² cos²(theta_0).
~~~

Квадраты могут добавить посторонние события, но это безопасно: внутри каждого
полученного интервала фактические корни f и направления проверяются напрямую.

Для 0<k<1 положим z=q^n, alpha=(1-k/2)/k. Тогда:

~~~
R=L+s alpha(1-z)
U=s q z
gV=(g/k)(1-qz)
Y=h_0+W_y n+(g/k)[n-alpha(1-z)]

K=(g/k)(L+s alpha)
  +[-(g/k)(s alpha+qL)-s q h_0-s q(W_y+g/k)n]z
D/4 = K² + [U²-(gV)²]r².
~~~

Слагаемые z² в K сокращаются. Символьной проверкой подтверждены тождество D/4
и следующие размерности функций:

| Функция | Вид | Максимум изолированных действительных нулей |
| --- | --- | --- |
| a | P0 + P1 z + P2 z², степени P: 0,0,0 | 2 |
| b | P0(n)+P1(n)z+P2 z², степени ≤1,1,0 | 4 |
| c и a+b+c | степени P ≤2,1,0 | по 5 |
| D/4 | степени P ≤2,2,2 | 8 |
| Каждая E_theta | степени P ≤2,2,2 | по 8 |
| r² | обычный многочлен степени ≤2 | 2 |

Эта таблица относится к постоянной скорости цели. Граница числа нулей относится
к ненулевым функциям. Две границы pitch вместе
дают не более 42 изолированных событий и 43 открытых интервалов независимо от
числа тиков горизонта. Реальные события часто совпадают или отсутствуют.

Почему число конечно: для F(n)=sum P_j(n) exp(lambda_j n) с действительными
различными lambda_j деление на один exp(lambda_0 n) сохраняет нули.
Дифференцирование уменьшает степень полинома при этом lambda_0 на единицу;
остальные сохраняют степень. Суммарная размерность уменьшается на один.
Индукция с теоремой Ролля даёт максимум sum(deg(P_j)+1)-1 нулей с кратностями.
Это также даёт алгоритм их изоляции, а не только верхнюю оценку.

При постоянном ускорении c и a+b+c имеют степени P: 4,2,0, а D/4 и E_theta —
4,4,4; K имеет степень 2 по n при z. Это подтверждено SymPy. Тогда общий резерв
становится ещё дороже: верхняя оценка — 70 событий вместо 42. Расширение существует
аналитически, но не является основанием использовать этот путь каждый тик.

### 5.4 Изолятор и перевод в целые интервалы

Изолятор рекурсивно находит нули производной от exp(-lambda_0 n)F(n).
Между соседними критическими точками эта функция монотонна и имеет не более
одного нуля. Проверяются концы и сами критические точки, включая касание без
смены знака. Простые корни уточняются защищённым Ньютоном/бисекцией в скобке.

После изоляции всех событий:

- На каждом открытом интервале пробная точка определяет наличие корня f и
  допустимого pitch; в обычном невырожденном режиме классификация постоянна.
- Целые n извлекаются через floor/ceil границ. Полный список всех n не создаётся.
- Вблизи границ проверяются соседние целые индексы непосредственно квадратным
  уравнением; отдельно учитывается событие, точно попавшее в целое n.
- Для выбора первого допустимого sweep достаточно первого целого в каждом
  допустимом интервале и конечного набора пограничных кандидатов.

При тождественно нулевой функции событий нужен отдельный разбор общих факторов
и постоянных корней на границе. Вертикальный случай, отсутствие гравитации,
тождественное квадратное уравнение и кратные решения нельзя просто пропустить.
Пока для такого случая нет проверенной специальной ветви, возвращается UNRESOLVED.
Утверждение о полноте для обычных ячеек не распространяется автоматически на
необработанные вырожденности.

Доказательство в точной арифметике не заменяет надёжный код: корни событий должны
иметь гарантированные интервалы, уточняемые до определения соседних целых индексов.
Касание и знак очень малого значения требуют интервальной арифметики/повышенной
точности. Исчерпание бюджета вычислений — UNRESOLVED, а не NO_POINT_SOLUTION.

При k=0 все функции событий становятся обычными многочленами степени не более 4.
При k=1 для n≥1 — степени не более 2; n=0 разбирается отдельно. Эти ветви не должны
проходить через log(q) или деление на k.

## 6. Финальная точность: реальные углы, hitbox и spread

### 6.1 Центр — предпочтение, hitbox — критерий

Из-за различия sweep и обновления позиции между соседними отрезками возможны
разрывы. Совпадение строго с центром при каждом n может не иметь решения даже
для реально поражаемой цели. Это было обнаружено при сопровождении навесной
ветви: один только квадратный решатель для центра иногда терял её.

Для фиксированного n и f множество точек sweep по всем направлениям — сфера
с центром C+(B_n+fV_n)G и радиусом R_n+fU_n, в обычной положительной геометрии.
Ближайшее к центру цели направление:

~~~
D_f=(dx,Y+f gV_n,dz)
u=D_f/|D_f|
signedResidual(f)=|D_f|-(R_n+fU_n).
~~~

Минимум абсолютного остатка находится среди f=0, f=1, корней квадратного
уравнения и стационарных точек остатка. Обозначив w=gV_n, получаем для w²>U_n²:

~~~
f_stationary=[U_n r/sqrt(w²-U_n²)-Y]/w.
~~~

Учитываются только допустимые f и соответствующий знак производной. Вырожденные
w=0/U=0 рассматриваются отдельно. Для ограничений pitch добавляются границы
theta_min/theta_max: при фиксированном угле sweep является отрезком, и ближайшая
точка находится обычной проекцией на этот отрезок за O(1). Yaw выбирается к
горизонтальной позиции цели в данном n. Нужен конечный набор алгебраических
кандидатов, а не дополнительный Newton или интегрирование.

Так получаем наименьшее евклидово отклонение от центра для данного sweep и
разрешённого конуса, затем проверяем реальный bbox. Это не является доказательством
полного поиска всех пересечений произвольного вытянутого bbox: при неуспехе могут
потребоваться другие точки/более полный разбор. Но разрешение на выстрел всегда
основано на фактическом пересечении, а не на сравнении только с центром.

В рабочем пути сначала пробуется точное совпадение с центром ближайшего sweep;
ближайшая точка и другие соседние n нужны при его отсутствии или неудаче финальной
проверки. Исследовательский прототип намеренно перебирает весь малый набор для
контроля, а не представляет оптимизированный горячий путь.

### 6.2 Независимая проверка найденного выстрела

Само направление u ещё не является физическим результатом установки.

1. Перевести u в углы установки с её ограничениями.
2. Округлить до реально используемых float и применить те же преобразования,
   что делает CBC/Create; получить действительные p_0 и v_0 центрального выстрела.
3. По аналитическим A_n, B_n и q^(n+1) вычислить один проверяемый sweep.
4. Выполнить фактический геометрический предикат попадания по bbox и reach.
5. Проверить нормализацию/длину sweep, модель среды, время жизни и состояние снаряда.

Проверка сохраняет исходный смысл из Power Radar: отбрасывает неверный выстрел.
Она не должна незаметно менять угол или подменять отсутствующее решение. Поиск
ближайшей точки и соседних LUT-ячеек относится к решателю, а проверяющая функция
читает фактические углы/позу и возвращает подтверждение либо отказ. Для прямой
проверки выбранного n не нужен новый проход по всем предшествующим тикам.

Для обычного горизонтального CannonMount при установившейся позе в идеальной
геометрии mount yaw=atan2(-u_x,u_z), mount pitch=возвышение theta для всех четырёх
начальных горизонтальных ориентаций. При этом entity.pitch имеет знак из
CannonMountBlockEntity.applyRotation. Знаки entity нельзя переносить на mount.
Финальное преобразование обязано использовать тот же прямой путь, что и запуск.

Обычные fireShot вызывают toGlobalVector с partialTicks=0, что читает предыдущую
позу через OrientedContraptionEntity; drop mortar использует 1. Для выстрела во
время поворота текущие поля и фактическая поза запуска могут различаться.
Адаптер должен учитывать этот порядок или требовать установившегося положения.

**Таблица тригонометрии:** VecHelper.rotate использует Mth.sin/cos с таблицей 65536
значений и float-индексацией, а не идеальные sin/cos. Шаг аргумента около 0.005493°.
Повторное применение atan2 с большим количеством знаков не устраняет эту ошибку.
Окрестность найденного угла следует проверять в пространстве фактических индексов
таблицы: сначала 3×3 соседних ячейки yaw/pitch, затем при необходимости небольшой
дополнительный бюджет. Изменение соседнего float часто оставляет тот же индекс LUT.

Геометрия после этих преобразований может немного изменить и эффективный L.
Поэтому последняя проверка использует реальные p_0/v_0, а не идеальную осевую модель.
Проверки нескольких направлений делят одни A_n/B_n: новый полный поиск не нужен.
Цель локального выбора — запас пересечения с hitbox и устойчивость направления,
а не обещание нулевого отклонения от математической точки любой ценой.

CBC проверяет:
- пересечение исходного projectile bbox с target bbox;
- либо клип sweep по target bbox, увеличенному на reach;
- попадание также зависит от широкофазной выборки, canHitEntity и onClip.

Например, простое попадание по увеличенному bbox вне широкой фазы нельзя считать
гарантированным попаданием CBC. Стремление к центру исходного bbox облегчает эту
проверку и даёт запас, но не отменяет сам предикат.

Projectile.getMovementToShoot прибавляет независимый случайный triangle-компонент
с параметром 0.0172275×spread к каждой оси нормализованного направления, затем
умножает на скорость. Направление с шумом повторно не нормализуется. Поэтому шум
меняет и модуль скорости; гарантировать попадание конкретного выстрела по центральной
траектории невозможно. Снижение промаха решателя и вероятность попадания при spread
должны оцениваться отдельно.

Для этой оценки также не нужна симуляция. В постоянной линейной среде при фиксированных
n и f отклонение точки sweep от центрального выстрела равно:

~~~
deltaH = s [A_n+f q^(n+1)] xi
xi_i = a (uniform1-uniform2), a=0.0172275×spread
|deltaH_i| ≤ |s [A_n+f q^(n+1)]| a
Var(deltaH_i) = s² [A_n+f q^(n+1)]² a²/6.
~~~

Это следует из фактического RandomSource.triangle:55 и линейности свободной модели.
Так можно за O(1) оценивать разброс и запас относительно bbox для разных ветвей.
Условия модели, широкая фаза и столкновения раньше выбранного sweep всё равно
проверяются отдельно. Эта оценка не является безусловной гарантией попадания в мире.

## 7. Численная устойчивость и границы обещаний

Для малых k нужны log1p/expm1 и отдельное устойчивое вычисление B_n.
Начало ряда:

~~~
A_n = n - n² k/2 + n(n-1)(2n-1) k²/12 + ...
B_n = n²/2 - n(n-1)(2n-1) k/12
      + n(n-1)²(n-2) k²/24 + ...
~~~

Критерий переключения должен ограничивать пространственную ошибку через s, g и n;
фиксированного правила «малый drag считать нулём» без оценки ошибки недостаточно.
Для функций событий при малом k коэффициенты в степенях 1/k плохо обусловлены:
предпочтительны устойчивые исходные выражения через A/B и пересчёт с повышенной
точностью при неопределённых знаках. Требуются масштабирование и общая арифметика
для функции и её производных.

Формулы точно решают рекурсию в вещественной арифметике, но не побитно повторяют
накопление округлений CBC. Пусть равномерные остатки одного реального шага относительно
идеальных уравнений ограничены eta_v и eta_p. Тогда при одинаковом запуске:

~~~
|error_v(n)| ≤ S_n eta_v
|error_p(n)| ≤ (1-k/2)(n-S_n)eta_v/k + n eta_p, k>0
|error_p(n)| ≤ n(n-1)eta_v/2 + n eta_p,            k=0.
~~~

К этой оценке добавляются ошибки вычисления самой формулы и фактического запуска.
eta должны оцениваться из диапазонов скоростей/координат и операций CBC; готовых
универсальных численных значений здесь не заявляется. Пространственные вычисления
желательно вести относительно C, а реальные мировые округления учитывать отдельно.
Финальная проверка bbox должна иметь запас больше вычисленного бюджета ошибки.

При произвольных препятствиях/жидкостях нельзя аналитически гарантировать свободный
полёт только по параметрам выстрела: CBC может изменить движение раньше выбранного n.
Проверка мировой трассы — отдельная пространственная задача с собственным бюджетом;
её стоимость нельзя честно объявлять O(1) для произвольного мира. Отсутствие такой
проверки отмечается отдельным признаком, а не считается разрешением на выстрел.

## 8. Исполнение и стоимость

Этот раздел сохраняет оценку ранее исследованного поиска по времени. Текущий
приоритет для заданной точки — прямое повторное решение прежнего sweep из раздела
13; там приведены новые проверки. Их не следует смешивать с прежними замерами.

~~~
solve(input, previous):
    profile = obtainActualCbcLaunchProfile(input)
    if unsupported profile or invalid observation:
        return UNSUPPORTED / UNAVAILABLE

    coefficients = prepareConstantParameters(profile)
    if conservativeRangeOrLifetimeBoundProvesNoPointSolution(input):
        return NO_POINT_SOLUTION_IN_HORIZON
    root = continueRequestedMotionRoot(input, previous.requestedBranch)
    if root unavailable:
        roots = isolateRootsOfSingleAnalyticInterceptFunction(input)
        root = chooseRequestedBranchAfterCbcChecks(roots)
    candidates = exactOrNearestCbcSweepCandidates(neighborIntegers(root))

    if candidates empty and difficult boundary case:
        windows = budgetedReserveEventSearch(input)
        if uncertain:
            return UNRESOLVED
        candidates = exactOrNearestCbcSweepCandidates(boundaries(windows))

    for suitable candidate:
        physicalDirections = cbcForwardPoseAndNearbyLutCells(candidate)
        validateAnalyticallyAtCandidateSweep(physicalDirections, actualTargetBox)
        choose acceptable direction with geometric margin and branch continuity

    if a verified candidate exists:
        return SOLVED(direction, n, f, modelRevision, verificationFlags)
    if exhaustive search and all required model conditions certified:
        return NO_POINT_SOLUTION_IN_HORIZON
    return UNRESOLVED
~~~

Если требования говорят «самая ранняя возможная ветвь», быстрый успех сам по себе
не доказывает оптимальность: нужен полный поиск или сохранённые актуальные границы.
По умолчанию для сопровождения важнее подтверждённое попадание и устойчивость ветви.
Нельзя безусловно называть первое по времени решение «самым низким pitch» для
произвольно движущейся цели.

Быстрый путь: несколько оценок F/F'/F'' для выбранной ветви, 1–3 аналитических
состояния около найденного sweep, квадратные уравнения/ближайшие точки и ограниченный
набор геометрических проверок; память O(1) на сохраняемую ветвь.
Смена профиля снаряда/заряда/геометрии/измерения инвалидирует соответствующие
коэффициенты. История всех траекторий не хранится.

Полный путь: стоимость зависит от размерности функций событий и точности изоляции,
а не от прохода через N последовательных состояний. Уточнение корней зависит
также от ширины горизонта/допуска и обусловленности. Этот путь существенно сложнее
и может потребовать больше оценок функций, чем старый Newton по pitch.
Исследовательский высокоточный изолятор выполняет сотни/тысячи оценок: его нельзя
назначать обычным пересчётом каждой пушки каждый тик или объявлять уже оптимизированным.

Кешируется лишь подсказка ветви и неизменные параметры профиля. Любой принятый
кандидат перепроверяется по свежему положению/скорости цели и реальной позе запуска.
contentVersion сети не является гарантией свежести sampledTick.

### Подсчёт операций в сравнении с Power Radar, 2026-10-29

Для проверки количества вычислений созданы временные копии настоящих
LinearDragAimSolver/LinearDragTrajectory и WeaponBallistics в
/tmp/cbc_operation_counts. В копиях добавлены счётчики; минимальный Vec3 содержит
только используемые поля. Исходный Power Radar не менялся. Подсчитаны вызовы
аналитического evaluate и отдельных Math-функций, без измерения наносекунд.

Во всех примерах k=0.01, L=0, цель неподвижна, разрешён pitch от -45° до 60°.
Для автопушки использован старый быстрый путь с переходом на полный при необходимости.
Новый прототип использует соответствующий своему CBC lifetime горизонт; старый код
сохраняет собственное правило lifetime+1 и интерполяцию между позициями. Поэтому это
сравнение фактических путей на одинаковых основных входах, не тождественных предикатов
попадания. Во всех строках речь о полном пересчёте без попадания в кеш.

| Сценарий: s,g,T,r,h | Старый evaluate | Старые pow / log | Новый полный изолятор: оценки функций / квадратные задачи |
| --- | --- | --- | --- |
| Автопушка: 5,0.05,60,100,0 | 5 | 21 / 10 | 1034 / 20 |
| Автопушка: 5,0.05,60,180,0 | 6 | 25 / 12 | 850 / 20 |
| Большая пушка: 8,0.05,600,200,40 | 5 | 21 / 10 | 2572 / 49 |
| Явно далёкая цель: 8,0.05,600,5000,0 | 0 | 1 / 0 | 1925 / 30 |

В старом evaluate на обычном интервале с n>1 выполняются 4 pow, 2 log, 1 sin,
1 cos и обычная арифметика; подготовка добавляет pow и acos. В коде максимум 8
шагов Ньютона и общий предел 24 итерации на отдельный поиск экстремума/корня.
Один полный статический solve при поиске экстремума и обеих ветвей может иметь
до 77 вызовов evaluate, но в приведённых сценариях завершился намного раньше.

Счётчик нового изолятора учитывает также оценки знака в критических точках,
которые раньше не входили в неполный отладочный EVALS. Один вызов функции событий
не равен по работе одному старому evaluate. Прототип использует mpmath precision=60,
уточнение до порядка 1e-25 и повторно считает exp для нескольких слагаемых вместо
совместного вычисления z и z². Это сознательно исследовательская, неоптимизированная
реализация. По этим числам нельзя получать отношение реального CPU-времени Python
и Java, но и объявлять полный изолятор более дешёвым оснований нет.

На тех же трёх достижимых примерах проверка найденного n и двух соседних потребовала
ровно 3 квадратные задачи и ни одной оценки функций событий. Текущая прямая функция
candidates заново вычисляет q^n; в рабочем сопровождении коэффициенты этих 1–3 тиков
можно сохранять до изменения профиля/индекса. Самостоятельного готового пути сопровождения,
финальной LUT/hitbox-проверки и соответствующего Java-замера пока нет.

В старой системе внешний TargetLeadSolver делает до 4 статических расчётов при
упреждении: начальный и 3 уточнения. Затем BallisticTrajectoryValidator может
выполнить один или два прохода длиной до 600 шагов. Проверка препятствий способна
добавлять обращения к миру. Однако кеш упреждения имеет TTL до 3 тиков, а кеш
валидатора — до 2/5 тиков при успешном результате и до 3 при неудаче. Сравнивать
новый полный пересчёт с этими кешированными обновлениями без поправки нельзя.

Практическое решение по стоимости:

1. Основной путь — прогноз на прежний n и новое квадратное решение этого sweep.
   Если он не подходит, выполняется короткая коррекция времени с новым прогнозом
   и алгебраическое уточнение sweep. Текущий вариант остатка описан в разделе 14.
2. Полный изолятор — резерв для поиска ветвей/подтверждённого отказа, с бюджетом;
   исчерпание бюджета даёт UNRESOLVED.
3. До любого сложного поиска нужны дешёвые доказательные отсечения. Например, для
   L≥0 горизонтальный радиус sweep ограничен R_N+U_N. Минимальное горизонтальное
   расстояние линейно движущейся цели на горизонте находится по вершине квадратной
   функции расстояния. Если этот минимум больше радиуса, отказ определяется одной
   аналитической оценкой, а не 1925 оценками из последней строки таблицы.
   Для ускоренной цели можно сначала ограничить каждый горизонтальный квадратный
   полином по концам и вершине, получить охватывающий прямоугольник и нижнюю оценку
   расстояния до него. Это консервативное O(1)-отсечение. Более точный минимум
   расстояния требует корней кубической производной, также без прохода по тикам.
4. Главный ожидаемый выигрыш — устранение потикового валидатора и повторных внешних
   согласований упреждения. Его ещё нужно подтвердить на одинаковых задачах после
   реализации быстрого пути и корректной геометрической проверки.

### Как оценивать производительность для соло и сервера

Решатель выполняется на логическом сервере. В одиночной игре это встроенный сервер;
повторный расчёт в клиентском рендере не нужен. Частота наблюдения/сопровождения
привязывается к серверным тикам, а не к FPS.

Сравнение нужно проводить в одном JVM на одинаковых последовательностях P/V/a,
одинаковых профилях CBC и выбранных режимах. Нужны отдельные сценарии: статика,
скорость, ускорение, LOW/HIGH, переключение режима, исчезновение ветви, предел
дальности и массовый захват недостижимых целей. Отдельно измеряются:

- Тёплое обновление выбранной ветви и обновление сразу двух ветвей.
- Холодный захват, резервный поиск и доля переходов к ним.
- Финальная проверка, а при её наличии — проверка препятствий.
- p50/p95/p99 времени, выделения байтов на запрос, число exp/log/pow,
  число оценок F и алгебраических кандидатов, доля отказов проверки.
- Ошибка и попадания по независимой физике CBC; быстрый, но неверный результат
  не считается преимуществом производительности.

**Нагрузочная постановка:** M независимых пар «пушка → своя цель», включая M=1000
как завышенный стресс-тест. Совпадающие цели, общий результат наведения и дедупликация
запросов не предполагаются. Слово «одновременно» означает нагрузку за один серверный
тик, а не создание отдельного потока ОС для каждой пушки. Сначала измеряется один
пакет независимых задач; многопоточность не заменяет оценку стоимости алгоритма.
Если все 1000 пар обновляются каждый тик при 20 TPS, это 20 000 запросов/секунду.
Например, выделенные на весь пакет 2 мс означали бы в среднем 2 мкс на пару вместе
с проверкой. Это пример перевода бюджета в требование, не замер и не обещание.

Для M обновляемых пушек средняя суммарная цена тика приблизительно
M*C_warm + число_захватов*C_cold + цена_проверок. Но защищать тик нужно по хвостам,
а не только по среднему: холодные операции имеют общий временной/итерационный
бюджет и очередь, а активные ветви получают приоритет. Значение бюджета выбирается
после Java-замеров; произвольные микросекунды здесь не выдаются за факт.
При исчерпании бюджета устаревшие углы не становятся разрешением на выстрел:
нужна свежая проверка или ожидание расчёта.

Отдельная обязательная серия — последовательности снимков с плавно меняющимся a,
поворотами, остановками, резким разворотом и сменой цели. Для каждого снимка строится
именно его прогноз X_j. Правильность выстрела проверяется независимым эталоном CBC
по этому прогнозу. Будущие манёвры генератора после снимка не являются ошибкой
баллистического решения. Можно отдельно измерять качество предположения о движении,
но смешивать эту метрику с точностью решателя нельзя.

Эта серия должна выявить стоимость восстановления: долю успешных обновлений
с прошлого корня, число оценок F_j, долю новых захватов и задержку до свежего
допустимого решения. Нужны и несинхронные изменения 1000 разных целей, и специально
совпавший по времени скачок всех входов. Последний сценарий проверяет общий бюджет
и очередь; хорошие средние результаты плавного сопровождения его не заменяют.
Полный поиск в эталоне теста допустим и не входит в измеряемый рабочий путь.

Нельзя сравнивать только количество вызовов F: новая F делит одну экспоненту между
значением и производными и не вызывает sin/cos/log внутри обычной итерации.
Это другой набор операций, а не уже измеренное отношение CPU-времени.
Старые повторные 4 pow можно сократить при рефакторинге —
такой улучшенный baseline тоже следует учитывать, чтобы не приписывать новому
математическому подходу выигрыш от очевидного кеширования старых вычислений.

## 9. Квадратичное сопротивление и другие неподдержанные режимы

Прочитаны 18 штатных JSON в munition_properties/projectiles проверенного коммита:
quadratic_drag=true не найден; свойство false либо отсутствует.

При quadratic_drag=true k_n=min(d |v_n|,1), постоянной геометрической прогрессии нет.
Общее точное аналитическое решение здесь не выведено. Это не доказательство
невозможности его существования. Для текущего этапа — отдельный UNSUPPORTED_QUADRATIC;
линейная модель не подставляется молча, потиковая симуляция основным путём не становится.
Специальный решатель для будущих боеприпасов можно разработать независимо.

Уточнение 2026-10-31: исследовать такую ветвь имеет смысл, но не как обязательную
зависимость линейного ядра. Newton как метод поиска угла применим и к другой модели;
трудность — быстро и достаточно точно вычислять её траекторию и производную ошибки.
При квадратичном drag коэффициент торможения зависит от скорости, а скорость при
наличии гравитации зависит от предыдущего движения и начального pitch. Общие для
всех углов A_n/B_n и сфера радиуса R_n больше не следуют из линейной рекурсии.
Поэтому дешёвый повторный квадратный расчёт нового направления не переносится
автоматически. Случай постоянной плотности всё равно остаётся дискретной физикой
CBC; решение непрерывного дифференциального уравнения само по себе не будет её
точным воспроизведением.

Рабочий исследовательский вариант при отсутствии точной прямой формулы — заранее
подготовленная аппроксимация/таблица для профиля снаряда с измеренной ошибкой,
а затем дешёвое уточнение. Это компромисс с подготовкой, памятью и точностью;
не доказанная готовая замена. Потиковый интегратор на каждую оценку Newton имел бы
порядок O(I*N) и не выполняет текущее требование основного пути без симуляции.
Сейчас точная O(1)-формула для этой ветви не получена, и она не объявляется готовой.

Также отдельно проверяются изменяющие поведение снаряды: например, MortarStoneProjectile
отмечает превышение заряда через setChargePower. Проверка способности выстрелить,
фузея и onClip — обязанности CBC-адаптера и проверки применимости, а не произвольной
баллистической поправки.

В LiveResult пока нет скорости и bbox. Для математического ядра они являются входами.
Будущая интеграция должна получать разрешённое серверное измерение наблюдаемой цели
с согласованными временами. Замороженная память радара не является свежим sample;
клиентский снимок не используется для авторитетного наведения.

### Совпадающее математическое ядро

В `targeting/LinearDragTrajectory.java:70–122` уже используются `q=1-drag`,
`scale=1-drag/2` и `S=(1-q^n)/drag`. Старая формула вертикальной координаты:

```text
y_n-y_0 = scale [v_y S - (g/k)(n-S)] - g n/2.
```

Поскольку `scale+k/2=1`, коэффициент при g равен `(n-scale S)/k = B_n`.
Это алгебраически то же ядро, что в разделе 2 данного документа, при G_y=-g.
Его наличие и отказ от потиковой симуляции в прямом расчёте не являются новым
преимуществом нашего варианта над старым проектом.

В `targeting/LinearDragAimSolver.java:253–312` неизвестной служит pitch:
логарифмом определяется номер тика пересечения горизонтальной дальности, затем
аналитически вычисляются позиции соседних целых тиков и доля интерполяции между ними.
Здесь нет последовательного проигрывания полёта по всем тикам.

В `solve`, `solvePeak` и `solveBranch` сначала ищется максимум высоты по pitch,
затем корни на двух ветвях. Используются аналитические первая/вторая производные,
до 8 шагов Ньютона с защитой интервалом и затем бисекция до общего лимита 24 итерации.
Для автопушки есть отдельный быстрый путь при ограничении углов временем жизни.
Выбор защищённого Ньютона сам по себе также уже присутствует в старом проекте.

В `targeting/TargetLeadSolver.java:64–81` упреждение строится внешними тремя
итерациями: прогноз точки цели по прежнему времени → новый статический расчёт →
обновление времени. В нашем варианте постоянная скорость цели входит непосредственно
в функцию времени, что позволяет исследовать совместное согласование одной задачей.
Выигрыш по скорости или устойчивости ещё не установлен.

### Что требует пересмотра

1. **Отрезок попадания.** `LinearDragAimSolver.java:270–288` интерполирует p_(j-1)
   и p_j. `BallisticTrajectoryValidator.java:94–99` проверяет такой же отрезок
   между позициями, с вкладом a/2. Проверенный CBC использует p_n → p_n+v_n+a_n.
   Поэтому согласие старого решателя со старым валидатором не доказывает совпадения
   с CBC. Возможное влияние нужно оценивать на hitbox, а не только на точку.
2. **Соглашение о времени.** В `LinearDragAimSolver.java:311` возвращается
   `hitTick+fraction`, хотя геометрический отрезок начинается в `hitTick-1`.
   `TargetLeadSolver.java:491` возвращает ту же величину. Относительно собственных
   позиций это дополнительный тик; внешний прогноз цели использует время напрямую.
   Например, интерполяция посередине первого шага имеет геометрическое время 0.5,
   а API выдаёт 1.5. Если нужен отдельный тик задержки запуска, его следует задавать
   явно вне определения физического времени полёта.
3. **Потиковая работа после аналитики.** `BallisticTrajectoryValidator.java:84–132`
   всё равно моделирует полёт до 600 шагов. При промахе `validate` может повторить

   `TargetControllerBlockEntity.java:1160–1254`, поэтому нельзя утверждать, что такая
   цена платится каждый тик. Однако основной путь при промахе кеша включает симуляцию

4. **Фактические параметры CBC.** `compat/createbigcannons/TargetControllerCbcCompat.java:331`

   `ballisticNumbers:595–603` читает базовые gravity/drag из компонента, а не эффективные
   модификаторы измерения/среды. Переносить эти допущения в новую интеграцию нельзя.
5. **Бюджет решения.** `LinearDragAimSolver.solveBranch:250` может вернуть лучший

## 13. Текущий основной алгоритм: заданная точка и повторное использование решения

### 13.1 Контракт и порядок поиска

Входы: точка X, центр/геометрия запуска, фактический профиль CBC, диапазон pitch,
горизонт, режим LOW/HIGH, пространственный допуск и необязательный кеш ветви.
Выходы: pitch/yaw, n/f выбранного sweep, остаточная ошибка, статус и новый кеш.
f — геометрическая доля sweep, а не дополнительная доля времени движения цели.
Скорость и ускорение цели не входят в этот контракт. Вычислитель упреждения
использует те же примитивы через отдельный координатор; связь описана в разделе 14.

Порядок для 0≤k<1 и обычной осевой геометрии:

1. Вычислить r=hypot(X_x-C_x,X_z-C_z), h=X_y-C_y и yaw к точке.
2. При пригодном кеше решить квадратное уравнение раздела 4 для прежнего n,
   уже с новыми r/h. Это новое точное решение, а не сохранённый старый угол.
3. При необходимости попробовать фиксированное число соседей, например n−1/n+1.
   Не расширять этот поиск линейным проходом до горизонта.
4. Проверить принадлежность выбранной семье LOW/HIGH и фактический результат углов.
5. Если быстрый путь не помог, получить кандидатов поиском с нуля, описанным ниже.
6. Вернуть направление только после проверки. Неудача ограниченного быстрого пути
   не доказывает отсутствие решения.

Кеш содержит профиль, n, q^n, A_n/B_n/S_n, выбранную семью и прошлое направление.
Для того же n новые log/exp/pow не требуются: меняются коэффициенты квадратного
уравнения через координаты цели. Для соседнего n коэффициенты обновляются за O(1):

~~~
z_(n+1)=q z_n
S_(n+1)=S_n+z_n
A_(n+1)=A_n+(1-k/2)z_n
B_(n+1)=B_n+(1-k/2)S_n+1/2.
~~~

Это переход между двумя коэффициентами, а не симуляция пути снаряда. При длительном
сопровождении нужно учитывать накопление округления при таких переходах и при
необходимости восстанавливать коэффициенты напрямую. Изменение баллистического
профиля инвалидирует соответствующий кеш. Близость точек не обязательна для
попытки: результат проверяется заново, а не принимается по величине перемещения.

Частый путь теперь может вообще не использовать Newton. Квадратное уравнение
требует одного sqrt и обычной арифметики; вычисление углов, проверка применимости
модели и фактической позы имеют отдельную стоимость. Это не утверждение, что весь
запрос выполняется без трансцендентных функций.

### 13.2 Поиск с нуля через наклон ствола

Положим m=tan(theta), r>0, s>0, L≥0, g>0, 0<k<1, ell=−log(q),
alpha=(1-k/2)/k. Для вспомогательной гладкой траектории, точно совпадающей с
позициями CBC в целые моменты, горизонтальное попадание определяет:

~~~
rho = r sqrt(1+m²)
A = (rho-L)/s
z = 1-A/alpha
t = log(z)/log(q)
B = (t-A)/k
H(m) = r m - h - g B.
~~~

H — ошибка высоты этой вспомогательной траектории. H=0 ещё не является
подтверждённым решением реального collision sweep. Его назначение — быстро
локализовать все допустимые точные кандидаты.

Производные по A:

~~~
B_A  = [1/(ell(alpha-A))−1]/k
B_AA = 1/[k ell(alpha-A)²] > 0.
~~~

При A≥A_c=alpha−1/ell имеем B_A≥0. Функция A(m) выпукла, поэтому
H''(m)=−g[B_AA(A')²+B_A A'']<0 в обычном невырожденном случае.
Следовательно, на связном допустимом интервале H имеет не больше одного максимума;
по обе стороны от него уровни находятся защищённым Newton/бисекцией в скобке.

Случай n=0 решается непосредственно квадратным уравнением. Для n≥1 достаточно
ограничить rho снизу значением R_1=L+s(1-k/2): тогда A≥A_1>A_c. Это сохраняет
доказательство и для близких к пушке точек. Если r<R_1, область m разделяется
на отрицательный и положительный интервалы; нельзя искать корень через запрещённый
промежуток. Сверху rho ограничивается R_N+U_N для последнего допустимого sweep N.
Оба ограничения пересекаются с реальным диапазоном pitch.

Поиск максимума особенно дешёв: пусть R_inf=L+s alpha,

~~~
W(rho)  = (g/k)[1/(ell(R_inf-rho))−1/s]
W'(rho) = g/[k ell(R_inf-rho)²]
rho' = r m/sqrt(1+m²), rho''=r/(1+m²)^(3/2)
H'  = r−W rho'
H'' = −W'(rho')²−W rho''.
~~~

Для H'/H'' логарифм не нужен: только sqrt и арифметика. Оценка H добавляет один
log/log1p; sin/cos/atan и pow внутри поиска отсутствуют. Максимум не зависит от
высоты h и может переиспользоваться, если меняется только высота точки.
Для k=0 используются t=A и B=A²/2; та же вогнутость получается без логарифма.

### 13.3 Почему достаточно узких областей, а не всех тиков

В выбранном sweep радиальная координата rho=R_n+f U_n. Ей соответствует
t=n+delta в гладкой формуле. Из геометрической суммы следует:

~~~
DeltaB(delta) = B_sweep−B_smooth
             = [alpha/q (1−q^delta)−delta]/k
0≤delta≤delta_end<1
0≤DeltaB≤1/(2q).
~~~

Верхняя граница не зависит от n, s и L. При k=0 точно
DeltaB=delta−delta²/2, поэтому 0≤DeltaB≤1/2. Следовательно, любое точное
попадание CBC в заданную точку обязательно удовлетворяет:

~~~
0 ≤ H(m) ≤ E,   E=g/(2q).
~~~

При обычных k=.01 и g=.05 это полоса по высоте шириной около 0.025253 блока.
Это расхождение вспомогательной функции с sweep, а не разрешённая ошибка выстрела.
Каждый окончательный кандидат всё равно решается по точному квадратному уравнению.

Вогнутость H позволяет найти области 0≤H≤E по её максимуму и корням двух уровней.
Обычно это отдельные области настильной и навесной семей. При сближении около
максимума области могут соединиться; разбор должен учитывать слияние, а не
перебрасывать Newton между семьями. Для отсечения ветви после обновления точки
можно использовать знак свежей H'; вблизи максимума нужен повторный захват.

Каждая область переводится в интервал t(m); при пересечении m=0 она делится
на монотонные части. Из интервалов с округлением наружу выводятся возможные целые n.
Если их мало, выполняются только соответствующие квадратные решения. Если диапазон
широк, включается резервный аналитический поиск событий внутри области, а не
перебор каждого n. Для обычного быстрого поиска можно сначала найти корень H=0
нужной семьи и попробовать соседние n; границы H=E нужны для полноты при неуспехе.

Отсутствие корня гладкого уравнения в допустимой области и подтверждённый H<0
исключают точное решение CBC. Наличие гладкого корня само по себе его не гарантирует:
у sweep имеются разрывы, а также ограничения f и pitch. Ядро точки не должно
маскировать это выбором ближайшего попадания в bbox. Работа по bbox остаётся
явным дополнительным режимом с собственным критерием успеха.

### 13.4 Устойчивость и резерв

Обратное преобразование по углу имеет обусловленность:

~~~
dt/drho = 1/[ell(R_inf-rho)].
~~~

Возле горизонтальной асимптоты вычитание R_inf−rho может потерять разряды.
Уточнять m до множества десятичных знаков бессмысленно: надо сменить переменную.
При недостаточной точности границ n используется статическая функция времени:

~~~
F(t)=r²+[h+g B(t)]²−[L+s A(t)]².
~~~

Она не обращает насыщенную горизонтальную координату. Сначала можно попробовать
защищённый поиск с прежнего t; для полного восстановления остаётся аналитическая
изоляция событий/корней. В исследовательском тесте использован имеющийся
высокоточный изолятор событий. Его стоимость не принимается за нормальную цену
обновления каждой пушки.

Нужны отдельные ветви r=0, g=0, k=1, знаковых/вырожденных геометрий и условия
из раздела 2. Для g=0 наклон задаётся самой точкой и обычных двух дуг нет.
Для r=0 yaw не определяется координатами: допустимо сохранять текущий yaw,
а вертикальные направления проверять отдельно. Очень малое k требует устойчивых
рядов, уже обсуждавшихся в разделе 7. Исчерпание бюджета или неопределённый знак
не превращаются в NO_POINT_SOLUTION. Окончательное округление углов и проверка
позы CBC остаются обязательными.

### 13.5 Проверки нового варианта

Исследовательский код: `/tmp/cbc_static_point_research.py`. Это самостоятельный
математический прототип, не Java-реализация мода. Он проверяет найденные интервалы
по полному перебору n во внешнем эталоне и попадания — прямой независимой рекурсией
CBC. Эти циклы используются только в тесте, не входят в предложенный рабочий путь.

В серии поиска с нуля проверен 701 набор: случайные дальности/высоты,
k=0/.002/.01/.03/.1, разные скорости/offset/lifetime, близкие к максимуму случаи,
точки внутри горизонтального радиуса дула и границы n/f/pitch. В 4 наборах

соседями, весь запрос — не больше 8, включая n=0. Эти максимумы относятся к

описанный кеш коэффициентов. Поэтому из этих чисел нельзя выводить время запроса,

## 14. Связь решателя точки с упреждением

### 14.1 Разделение ответственности и соглашение о времени

Три независимых части:

- Прогноз возвращает X(t), производную dX/dt и при необходимости d²X/dt².
  Он не знает о pitch, drag и выбранном стволе.
- Баллистическое ядро возвращает коэффициенты полёта в заданном t и решает
  `solvePointAtSweep(X,n,arc)` для конкретной точки. Оно не знает о UUID или движении цели.
- Координатор согласует прогноз с n, выбирает кандидатов и хранит состояние
  выбранной семьи. Он использует общие формулы, не вызывает полный solvePoint
  на каждом шаге согласования времени.

Разные пушки и цели имеют собственное состояние. Общий target cache не требуется
для работоспособности или оценки сложности этой схемы.

Пусть tau=возраст sample+задержка до запланированного запуска+согласование фаз
обработки сущности/снаряда. Для полиномиального прогноза:

~~~
X(t)=P+V(tau+t)+a(tau+t)²/2.
~~~

Вычисление P_launch и V_launch выполняется один раз, как в разделе 3.
При дискретном движении V=v+eta*a/2, eta∈{-1,0,1}; производная полинома не всегда
совпадает с сырым полем скорости сущности в тот же дискретный момент. Поэтому
координатор использует производную именно выбранного прогноза.

Все новые данные фиксируются одним снимком на запрос. Изменение запланированного
момента выстрела означает новое tau и новую проверку. Прошлое n задаёт начальное
приближение для НОВОГО выстрела; из него не вычитается автоматически один тик.

### 14.2 Частый путь: согласование сразу в прежнем sweep

Если есть сохранённый n, координатор получает X_n=X(n) и вызывает точечное ядро
именно для этого n. При успехе выполнено условие:

~~~
C+(R_n+f U_n)u+(B_n+f V_n)G = X(n),  0≤f≤1.
~~~

Слева — настоящий отрезок CBC, справа — прогноз видимой позиции цели в соответствующем
тике. Время и точка уже согласованы. Внешние итерации упреждения не нужны.
При неуспехе проверяется фиксированное число соседних n, причём для КАЖДОГО n
заново вычисляется X(n). Нельзя сдвинуть sweep и оставить прежнюю точку прогноза.
Коэффициенты прежнего и соседнего n используются по правилам раздела 13.

Это не команда целиться в текущее положение: X(n) уже содержит упреждение на n,
возраст sample и задержку запуска. При успешном быстром пути нужны полиномиальный
прогноз, квадратное уравнение и независимая финальная проверка.

### 14.3 Корректор времени без вложенных полных поисков pitch

Для поиска с нуля или восстановления можно получить начальное t из решения по
точке X(0). Это только начальное приближение. Недостижимость X(0) НЕ доказывает
недостижимость движущейся цели: она может позже войти в зону поражения.
При отсутствии такого начального решения используются другие приближения либо
резервный поиск на горизонте; отказ быстрого поиска имеет статус UNRESOLVED.

Вычисляем по тем же баллистическим коэффициентам:

~~~
D(t) = X(t)-C-B(t)G
R(t) = L+s A(t)
e(t) = |D(t)|-R(t)
e'(t) = D(t)·[X'(t)-B'(t)G]/|D(t)| - s A'(t).
~~~

e — пространственная невязка в блоках. Для обычного случая R>0 её нули совпадают
с нулями F=|D|²-R² из раздела 5, поэтому прежний алгебраический анализ F остаётся
полезным для полного захвата. Но шаги Newton вдали от корня у этих функций различны.
Для коррекции времени выбран нормированный по расстоянию остаток e:

~~~
t_new = t-e(t)/e'(t).
~~~

Одна оценка e/e' использует одно общее exp/expm1 для баллистики и один sqrt нормы.
Прогноз и его производная добавляют арифметику. Полного решения pitch внутри оценки
нет. При первом шаге из прежнего целого n коэффициенты уже сохранены, поэтому
новый exp не нужен. Вырождение |D|≈0 или e'≈0 обрабатывается отдельно.

Причина выбора e вместо F: даже в простом прямолинейном случае без drag/gravity
при X(t)=r+v*t и R(t)=L+s*t имеем e=r-L+(v-s)t. Newton для e решает эту задачу
одним поправочным шагом. Newton для квадрата F при старте r/s может выбрать
направление к отрицательному корню. Один дополнительный sqrt окупается устойчивостью
в таком сценарии; это обоснование выбора остатка, а не универсальный CPU-замер.

Корректор ограничен горизонтом и бюджетом оценок. В прототипе — максимум 12 оценок:
полный шаг либо до четырёх вариантов укорочения с проверкой уменьшения |e|.
При наличии надёжной скобки можно использовать бисекцию. Само уменьшение |e|
не доказывает сохранение семьи: каждый окончательный кандидат отдельно классифицируется.

### 14.4 Возврат к дискретному CBC и критерий успеха

Корень e нужен только для локализации n. После коррекции проверяется небольшой
фиксированный набор целых n около t, всегда с точкой X(n). Решение в данном n
снова получается точным квадратным уравнением. Именно эта пара n/X(n), а не
гладкое t, определяет проверяемое упреждение.

Критически: f — геометрическая доля sweep. Подстановка X(n+f) вместо X(n)
меняет принятую модель чтения bbox CBC и добавляет ошибку упреждения.
Время запуска и сдвиг фаз задаются через tau; их нельзя подменять прибавкой f.

Результат хранит как минимум углы/направление, n, f, X(n), версию снимка и
запланированный запуск. Согласованность проверяется по свежему прогнозу и
фактическому sweep. Номер n означает проверенный кандидат перехвата, а не
доказанный первый контакт с движущейся сущностью во всём мире: возможен более
ранний контакт, уже поражающий ту же цель. Поиск глобально первого контакта
и настройка взрывателя по нему — отдельное требование к проверяющему слою.

Для движущейся цели статическая граница 0≤H≤g/(2q) из раздела 13 не переносится
на e автоматически: между t и n меняется сама прогнозируемая точка. Поэтому
проверка только соседей корня e не является доказательством полного поиска.
При неудаче нужен резерв по точным событиям с X(n), либо UNRESOLVED при исчерпании
бюджета. Нельзя выдавать NO_INTERCEPTION только из-за отсутствия корня e или
неудачи четырёх соседних n. Аналогично полная проверка точки не доказывает
отсутствие попаданий в край ненулевого bbox.

### 14.5 LOW/HIGH и повторное использование результата

Для каждого кандидата рассматривается баллистическая семья относительно его
фиксированной точки X(n): настильная или навесная. В обычной области раздела 13
семьи различаются знаком H' по наклону. Возле слияния, при плохой обусловленности
и в специальных геометриях требуется полный разбор, а не произвольная метка.

При движении разные перехваты относятся к разным будущим точкам; их может быть
больше двух, в том числе несколько в одной семье. Координатор сохраняет допустимое
согласованное решение выбранной семьи. Он не обещает заново оптимизировать каждый
тик самый ранний перехват или глобально минимальный pitch. Для такой оптимизации
нужно дополнительно отслеживать остальные ветви и их появление, что стоит вычислений.
Переключение LOW/HIGH вызывает свежую проверку соответствующего отдельного кеша.

## 15. Стоимость относительно Power Radar: уточнение текущего варианта

Сравнение относится к свежему расчёту, когда старый кеш не вернул готовый результат.
Старый линейный решатель тоже использует аналитическую прямую формулу и Newton.
Поэтому сам отказ от симуляции внутри функции ошибки не является новым выигрышем.

| Часть | Старый проект | Текущий проектируемый вариант |
| --- | --- | --- |
| Оценка ошибки точки в обычном n>1 | 4 pow, 2 log, sin, cos | По tan(pitch): один log и sqrt; производная для максимума без log |
| Повторное наведение в прежнем n | Новый статический поиск при промахе кеша | Квадратное уравнение на свежую точку, коэффициенты сохранены |
| Согласование упреждения | До 4 полных статических поисков | Сначала X(n) и одно квадратное решение; при неуспехе корректор e/e' |
| Баллистическая проверка кандидата | До 600 шагов, иногда второй проход | Прямая формула выбранного sweep; проверка применимости модели отдельно |

Если I — число оценок в статическом поиске, J — число оценок корректора времени,
N — длительность проверяемого полёта, то старый свежий линейный путь имеет порядок
O(I+N), с прежним упреждением — O(K*I+N), K≤4. Новый частый путь имеет фиксированное
число алгебраических кандидатов; путь с корректором — O(J) плюс эти кандидаты.
Подготовка первого решения и резервная изоляция имеют отдельную стоимость.
Нельзя объявлять их универсально O(1), гарантировать одинаковое число итераций
или игнорировать их одновременный запуск у множества пушек.

Ожидаемый основной выигрыш — дешёвое свежее сопровождение и устранение O(N)
баллистической проверки. Холодный поиск не доказан быстрее старого на всех случаях;
дорогой полный изолятор способен быть существенно медленнее. У старого проекта
есть кеши, а повторные pow можно сократить рефакторингом. Отношение реального CPU-времени
и предел количества пушек определяются одинаковым Java-бенчмарком, не этим подсчётом.

## 16. Задержки: согласование прогноза и достижимого момента запуска

Реализация полного исследовательского цикла:
[research/cbc_pipeline.py](research/cbc_pipeline.py). Она использует баллистику
разделов 13–14. Решатель точки по-прежнему получает только X и профиль снаряда.
Координатор получает снимок цели, состояние привода, выбранную семью и кеш.
Все координаты в прототипе приведены к неподвижному центру установки C.

### 16.1 Единая шкала времени

Пусть t_s — тик снимка, t_0 — текущий тик, age=t_0-t_s, W — целая задержка
до spawn снаряда, sigma — сдвиг между spawn и состоянием цели, читаемым при первом
CBC-sweep. Тогда для sweep n прогнозируем цель на момент:

~~~
Delta = age + W + sigma + n
X(Delta) = P + (v + eta*a/2)*Delta + a*Delta²/2.
~~~

eta=−1 означает обновление позиции старой скоростью, eta=+1 — новой скоростью,
eta=0 — симметричный шаг. Это соглашение о смысле предоставленных P/v/a,
а не возможность произвольно выбрать более удобную формулу. Адаптер наблюдения
фиксирует соглашение один раз. В Snapshot.offset полного API должно быть 0:
координатор сам добавляет возраст, W и sigma и запрещает двойной учёт задержки.

Перед поиском переносим полином к выбранному запуску, tau=age+W+sigma:

~~~
P_launch = P + (v+eta*a/2)*tau + a*tau²/2
V_launch = v+eta*a/2 + a*tau
X_n = P_launch + V_launch*n + a*n²/2.
~~~

Внутри корректора используется этот же полином с вещественным t. Окончательный
кандидат всегда проверяется с X_n при целом n. Геометрическое f из квадратного
уравнения НЕ прибавляется ко времени цели. Здесь полностью сохраняется контракт
раздела 14: скорость и ускорение влияют на запрашиваемую точку, не на физику снаряда.

### 16.2 Время поворота, готовность и задержка команды

Адаптер привода предоставляет фактические скорости осей в градусах/тик,
текущую позу, позу, которую сейчас прочитает spawn, остаток перезарядки/cooldown,
задержку от допустимой команды до spawn и задержку отражения позы в transform.
Для свободного двустороннего привода с постоянными скоростями:

~~~
T_yaw   = ceil(abs(wrap180(yaw_desired-yaw_current)) / omega_yaw)
T_pitch = ceil(abs(pitch_desired-pitch_current) / omega_pitch)
T_turn  = max(T_yaw, T_pitch)              # одновременные оси
T_ready = max(T_turn + T_settle, ready_after)
W_required = T_ready + trigger_delay.
~~~

Если оси действительно работают последовательно, T_turn=T_yaw+T_pitch.
Нулевая скорость допустима только для оси, уже стоящей в требуемом направлении.
T_settle=0 при уже достигнутой и отражённой позе; иначе используется pose_lag.
Перезарядка может идти одновременно с поворотом, поэтому складывать оба времени
безусловно нельзя. trigger_delay — оставшаяся задержка ПОСЛЕ допустимой команды,
не полная длительность рабочего цикла механизма.

В CBC [CannonMountBlockEntity.tick](https://github.com/Cannoneers-of-Create/CreateBigCannons/blob/46a5d2ae9a53c1dc195919500e13f26ba812f2db/src/main/java/rbasamoyai/createbigcannons/cannon_control/cannon_mount/CannonMountBlockEntity.java#L143)
обновляет обе оси в одном тике, с ограничениями sequenced movement. Его
[getAngularSpeed](https://github.com/Cannoneers-of-Create/CreateBigCannons/blob/46a5d2ae9a53c1dc195919500e13f26ba812f2db/src/main/java/rbasamoyai/createbigcannons/cannon_control/cannon_mount/CannonMountBlockEntity.java#L317)
преобразует кинетическую скорость через convertToAngular и множитель 0.125.
Значения getYawSpeed/getPitchSpeed нельзя напрямую считать градусами/тик.
Направление двигателя, пределы хода, остановки и ограничения sequence обязан
учесть адаптер; формула кратчайшего wrap не обещает управлять любой механикой.

CBC использует трансформации с partialTicks=0 при запуске. Поэтому текущие поля
углов не всегда совпадают с позой spawn. Фиксированные pose_lag=1 и sigma=0/1
в тестах — явно заданные сценарии, не утверждение об универсальном порядке тиков
Minecraft. Игровой адаптер должен установить фактический порядок target/mount/entity
ticks и первого sweep. Задержка позы и sigma описывают разные явления.

### 16.3 Замыкание зависимости «точка → угол → время поворота → точка»

Начинаем с минимального W по готовности механизма и задержке выстрела. При
сопровождении сохраняем ещё не истёкший абсолютный launch_tick прежнего плана:
постоянное откладывание срока на каждом новом снимке иначе мешало бы выстрелить.
Для выбранного W решаем перехват, переводим направление в командные углы и
получаем W_required. Если W_required≤W, приводу хватает времени; если больше,
назначаем W:=W_required и пересчитываем прогноз с новым tau.

W внутри одного запроса только увеличивается. Это исключает колебание между
двумя округлёнными сроками поворота, но не доказывает существование решения.
По умолчанию разрешены четыре повышения W и заключительная проверка. Перед
последней проверкой можно взять верхнюю оценку времени достижения любой разрешённой
позы: до 180° по yaw и до дальней границы pitch. Она применима лишь при доступных
осях и корректном контракте привода. Если прогнозируемая цель к этому сроку
неперехватываема, возвращаем отказ поиска, а не вымышленное направление.

Согласованность с шагом 1 проверена независимой рекурсией цели: возраст снимка,
новый W, sigma и n учитываются ровно один раз. Решение допустимое, но запуск
не обязательно самый ранний: это осознанный выбор устойчивого сопровождения.

## 17. Полный порядок расчёта и граница команды на выстрел

1. Зафиксировать один неизменяемый снимок наблюдения, профиль снаряда и среды,
   геометрию, состояние привода, выбранную семью и соглашения о времени. Проверить
   значения, свежесть и поддерживаемость модели. Отозвать прежнее разрешение
   на выстрел; кеш направления/номера sweep остаётся только подсказкой.
2. Сверить идентичность цели, профиля и геометрии. При их изменении сбросить
   несовместимые кеши и резервные задачи. У LOW/HIGH отдельные кеши.
3. Выбрать W, составить прогноз из раздела 16. Проверить прежний n, затем n−1/n+1:
   для каждого номера заново получить X_n и решить точное квадратное уравнение.
4. Если быстрый путь не дал кандидата, выполнить консервативную проверку дальности
   всего допустимого окна. Затем начальное приближение и ограниченный корректор
   e/e' из раздела 14. При неудаче — ограниченный резерв из раздела 18.
5. Проверить семью, пределы ствола и доступность привода. Согласовать W с поворотом;
   при изменении W вернуться к шагу 3 с новым прогнозом. Не менять семью молча.
6. Преобразовать направление в командные углы и снова получить p0/v0 через прямой
   transform адаптера. При команде сейчас использовать именно наблюдаемую позу
   spawn. Аналитически построить реальный sweep p_n→p_n+v_(n+1) из этих p0/v0
   и проверить расстояние до свежего X_n. Не доверять сохранённому идеальному u/f.
7. Выдать план с command_tick, launch_tick, n, проверенной точкой, углами, семьёй,
   невязкой и полным ключом входов. Будущий план разрешает наведение, а не выстрел.
8. Непосредственно перед внешней командой атомарно сверить текущие входы и состояние
   с планом. Только затем один раз занять план через claim_trigger и передать
   команду игровому механизму. Прототип сам не вызывает игровой выстрел.

Критическое различие:

~~~
launch_tick  = now + W
command_tick = launch_tick - trigger_delay
READY        <=> проверенный command_tick == now.
~~~

Например, при уже наведённой пушке и trigger_delay=3 команда допустима сейчас,
а spawn произойдёт через три тика. Прогноз включает все три тика. Проверка W==0
для выдачи READY в таком случае была бы ошибкой и могла бы бесконечно откладывать
выстрел; регрессионный тест закрепляет правильное поведение.

После принятия необратимой команды состояние — WAITING_SPAWN. До подтверждения
реального spawn либо отмены удерживается исходная поза; новые цели и переключение
LOW/HIGH не меняют уже принятый план. Даже наступление ожидаемого launch_tick
само по себе не является подтверждением выстрела. acknowledge_trigger различает
запуск вовремя, запуск в другой тик и отмену/отказ. При фактически иной задержке
проверенность первоначального перехвата больше не гарантируется.

До принятия команды любой новый снимок, режим, геометрия, профиль, состояние
привода или тик требует свежей проверки. can_trigger требует TrackState: старый
объект READY нельзя повторно использовать после отзыва разрешения новым расчётом,
даже если передать ему прежние входы. claim_trigger исключает повторный запуск
одного плана. Под атомарностью здесь понимается последовательное исполнение на
владельце игрового состояния; блокировки и потоки сервера прототип не реализует.

Согласованность с задержками проверена сценарием полного наведения: цель движется,
каждый тик поступает новый снимок, привод поворачивается, предыдущая поза отражается
в spawn позднее. Расчёт достигает command_tick, а не только бесконечно выдаёт AIMING.

## 18. Неудачи, LOW/HIGH и ограниченный резерв

### 18.1 Значение результатов

| Статус | Смысл и дальнейшее действие |
| --- | --- |
| READY | Направление проверено; команду сейчас разрешает только успешный claim_trigger с теми же входами. |
| AIMING | Проверен будущий план. Поворачивать/удерживать; перед командой пересчитать и проверить. |
| WAITING_SPAWN | Команда уже принята. Держать исходную позу, ждать фактического подтверждения. |
| STALE_INPUT | Цель не наблюдается либо снимок старше разрешённого возраста. Ждать свежие данные. |
| INVALID_INPUT | Некорректные единицы/значения/время или нарушение контракта входов. |
| UNSUPPORTED_MODEL | Например, quadratic drag, k=1 или неприменимость требуемой линейной модели. |
| CONTROL_UNAVAILABLE | Механизм не позволяет управлять и удерживать позу запуска. |
| NO_POINT_IN_WINDOW | Консервативная граница исключила точку во всём разрешённом окне запусков и полёта. Не утверждает недостижимость края bbox. |
| NO_SELECTED_ARC | Доказанно отсутствует выбранная семья; сейчас отдельный случай g=0/HIGH. |
| SEARCH_PENDING | Резерв исчерпал лимит узлов и сохранил незавершённые интервалы. Выстрел запрещён. |
| UNRESOLVED | Поиск не дал проверенного решения; это не доказательство невозможности попадания. |
| DELAY_LIMIT | План требует запуска за пределами разрешённого окна ожидания. |
| VERIFY_REJECTED | Прямой transform/sweep не подтвердил выбранный кандидат с требуемым допуском. |
| BUDGET_EXHAUSTED | Исчерпан локальный/общий бюджет или достигнут дедлайн. Старого разрешения на выстрел нет. |

NO_POINT_AT_LAUNCH — внутренний результат резерва: исключены все sweep только
при одном фиксированном запуске. Его нельзя публиковать как отсутствие перехвата
при любом W. Координатор может попробовать другой разрешённый W; без глобального
доказательства окончательный отрицательный результат остаётся UNRESOLVED.

Исчезновение решения отзывает разрешение, но не обязано стирать численную подсказку.
Если цель вернулась, прежний n проверяется заново. Изменение LOW/HIGH отзывает
предыдущий план и выбирает отдельный кеш. Автоматического перехода на другую семью
нет. Для движущихся целей в одной семье может быть несколько перехватов;
сопровождаем допустимый непрерывный вариант, не обещаем глобально минимальный угол
или время. Слияние семей/касание и точная вертикаль в данном прототипе могут дать
UNRESOLVED: произвольная метка LOW/HIGH не подставляется.

### 18.2 Реализованный резерв

Резерв запускается после неудачи прежнего sweep, соседей и корректора времени,
либо для поиска кандидата, достижимого оставшимися доступными осями. Это ветвление
интервала целых n∈[0,N]. Для каждого интервала консервативно ограничиваются X_n,
гравитационный сдвиг и достижимая радиальная оболочка. Если оболочка и точка
разделены, отбрасываем весь интервал; иначе делим его пополам. Подсказка прежнего
n задаёт порядок обработки, но не исключает остальные интервалы.

В листе решается то же квадратное уравнение для конкретного n. Пустой ответ
double-решателя сам по себе ничего не доказывает. Для отрицательного доказательства
проверяется знак трёх интервальных коэффициентов полинома в базисе Bernstein
на f∈[0,1]. Неоднозначные знаки сохраняют UNRESOLVED. Арифметические границы
расширяются nextafter; q^n для этих границ вычисляется возведением в степень
за O(log n), без трансцендентных функций и без интегрирования траектории.

По умолчанию допускаются 96 узлов резерва на один его вызов. Общий лимит запроса
дополнительно ограничивает сумму всех вызовов при уточнениях W. Прерывание возвращает
текущий узел в очередь — незавершённый интервал не превращается в доказанно пустой.
Продолжение допустимо только при том же ключе: профиль, полином прогноза, выбранная
семья, абсолютный запуск, допуск и, при проверке привода, его состояние и адаптер.
Устаревшая задача сбрасывается. Новый снимок/движение привода могут потребовать
перезапуска; гарантии завершения сложного резерва при непрерывно меняющихся входах нет.

Резерв сначала ищет направление, достижимое к выбранному launch_tick. Если такой
кандидат не найден, может использовать сохранённый кандидат с более поздним запуском
и заново согласовать прогноз. Проверка выявила реальную ошибку первоначального
порядка: первое баллистическое решение требовало поворота, хотя другой перехват
той же семьи уже совпадал с текущей позой. Без фильтра по достижимости первая
находка сдвигала W и скрывала готовое решение. Этот случай исправлен и закреплён
тестом, где быстрый корректор не сходится, а резерв выдаёт READY на sweep n=70.

Потиковой симуляции нет ни в быстром пути, ни в резерве. Однако резерв может
выродиться в исследование множества отдельных n: худший полный проход имеет
до O(N) узлов и O(N log N) работы с приведёнными интервальными коэффициентами,
а не универсальную постоянную сложность. При заданных лимитах результатом будет
SEARCH_PENDING/UNRESOLVED, если закончить поиск не удалось. Исследованный полный
изолятор аналитических событий из раздела 5 в этот прототип не включён.

### 18.3 Бюджет множества независимых пушек

Ограничиваются: оценки корректора, повышения W, узлы резерва, суммарная работа
запроса и общий дедлайн партии. По умолчанию — 12 оценок e/e', четыре повышения W,
96 узлов на вызов резерва и 1600 условных единиц работы на запрос. Счётчики включают
прогноз, коэффициенты, квадратичные задачи, математические функции, привод и проверку.
Одна единица не равна фиксированному числу наносекунд: это диагностический счётчик.
Дедлайн проверяется между порциями работы, поэтому является мягким ограничением,
а не гарантией прерывания в точную наносекунду.

Для игрового планировщика нужен общий лимит времени на тик, отдельные квоты
быстрых запросов и резерва, очередность без голодания и ограничение числа живых
резервных задач. Пушки с подходящим временем команды имеют приоритет, остальные
переносятся в пределах свежести данных. Перед резервом полезно дать другим
пушкам выполнить дешёвый путь; один тяжёлый запрос не должен занимать весь бюджет.
Порядок обработки между тиками меняется. При нехватке времени снижается частота
пересчёта, а не точность проверки и не требование свежего разрешения на выстрел.

Исследовательский код реализует локальный/общий счётчик, общий дедлайн и перенос
остатка партии; полноценного справедливого игрового планировщика здесь нет.
Замер ниже специально показывает, почему одного счётчика операций недостаточно.
Старая поза может оставаться ориентиром для привода при перенесённом запросе,
но старый READY не даёт права выстрелить в новом тике.

а не доказывает его полноту. Для резервного поиска отдельно есть случай найденного
перехвата, пропущенного быстрым путём. Резкий разворот после принятой команды
не подменяет прогноз уже принятого выстрела.

### 19.1 Исправления, найденные при общей проверке

- Малый drag: вычисление B=(t−A)/k теряло значащие цифры. При k*max(1,|t|)<0.001
  используются шесть членов биномиального ряда B/B'; V вычисляется как A/c+q^n.
  Для соседних sweep производные обновляются устойчивыми равенствами
  B'_(n+1)=q B'_n+1 и B'_(n−1)=(B'_n−1)/q.
- Нулевая скорость около вершины при k=0 не нарушает модель: сопротивление всё
  равно равно нулю. Прежний общий запрет нормализации здесь давал лишний отказ;
  он снят для k=0. При k>0 применимость normalize проверяется отдельно.
- Проверка применимости сопротивления сначала использует кешируемую границу
  минимальной скорости по профилю и разрешённым углам. Если её недостаточно,
  проверяются начало, конец и ограниченное число целых соседей аналитического
  минимума |v_j|². Прохода через все j нет. Неподтверждённый режим не используется
  для выдачи глобального отрицательного доказательства.
- Отрезок столкновения короче 0.01 отклоняется согласно CBC. Проверяется именно
  p_n→p_n+v_(n+1), а не отрезок между двумя сохранёнными позициями снаряда.
- Исправлен выбор резервного кандидата с учётом текущего срока поворота; уточнена
  граница READY между командой и spawn; состояние стало обязательным для проверки
  разрешения. Эти изменения проверены совместно с прежними шагами, не только изолированно.

### 19.2 Полная стоимость на 1000 независимых парах

Сценарий: отдельные профиль/цель/кеш для каждой пушки, половина LOW, половина HIGH.
Начальные цели на дальностях примерно 320–420 блоков; далее свежие снимки
и движение привода. Скорости снарядов немного различаются, общий профильный кеш
между всеми пушками не подменяет работу. Измерение однопоточное, Python 3.14.8,
Linux x86_64, со включёнными счётчиками. Это нагрузочная серия, а не Java/TPS-замер.

Время запроса включает прогноз, поиск углов, повторные согласования W, резерв,
прямую проверку позы/sweep и финальную проверку разрешения для READY. Генерация
тестовых входов и потиковые эталоны не входят. «Вся партия» дополнительно включает
создание объектов запроса и сбор статистики, поэтому больше суммы времени решателя.
Сырые результаты: [research/cbc_pipeline_results.json](research/cbc_pipeline_results.json),
запуск 2026-10-31, 11:55 UTC.

Первые 1000 запросов дали AIMING. При сопровождении все 1000 запросов каждого
тика дали план; во втором тике два READY, в третьем четыре. В варианте разворота
без дедлайна: 31 AIMING, 160 UNRESOLVED, один BUDGET_EXHAUSTED, 808 запросов отложены.
С дедлайном первый тяжёлый запрос получил BUDGET_EXHAUSTED, остальные 999 отложены;
это демонстрация ограничения нагрузки, **не** обработки тысячи пушек за 5 мс.
В последней серии все 1000 запросов получили NO_POINT_IN_WINDOW.

Частый полный запрос первого/второго тика сопровождения здесь содержит одну
квадратичную задачу, два прогноза точки, одну проверку привода и один прямой
контроль sweep. Подсчитано 18 единиц работы: в том числе 2 sqrt, hypot, 2 atan2,
2 sin, 2 cos и один exp при независимом пересчёте коэффициентов проверки.
Отсутствие exp при повторном **поиске** в прежнем n не означает отсутствия exp
во всём запросе. Ранее эти стоимости было бы неправильно смешивать.

Измерение позволило убрать глобальные интервальные границы из успешного пути
прежнего n/соседей: до изменения медиана сопровождения была около 228 мкс,
после — около 140 мкс в этой среде. Профиль и его границы также кешируются.
Проверка готового кандидата сохранена. Это локальное наблюдение, не сопоставление
с Power Radar и не прогноз ускорения Java.

Python-прототип в таком виде не обслуживает тысячу пересчётов каждый 50-мс тик:
даже нормальное сопровождение всей партии дороже. Глобальный дедлайн сохраняет
бюджет, но не пропускную способность. Для оценки игрового предела нужен Java-замер
с реальным адаптером и планировщиком; нельзя выводить его из числа exp или из
обрыва партии по таймеру. Холодные запросы и синхронные манёвры обязательно входят
в такой замер, иначе хвост задержек будет скрыт.

## 20. Зафиксированный результат и границы готовности

Шаги 1–5 согласованы в одном исследовательском цикле: аналитическая баллистика
точки → прогноз X_n → срок запуска с поворотом → проверенная поза → одноразовая
команда. Повторные решения используют прежний n/коэффициенты; новые снимки
не меняют физическую модель CBC. При неудаче есть ограниченный резерв и явные
статусы, не выдающие отсутствие сходимости за доказанную недостижимость.

Воспроизведение из корня проекта, без сторонних Python-пакетов:

~~~sh
python3 -B research/cbc_lead_model.py
python3 -B -m unittest research.test_cbc_pipeline -v
python3 -B research/benchmark_cbc_pipeline.py --pairs 1000 --warm-frames 3 --output research/cbc_pipeline_results.json
~~~

Это проверенная модель для неизменного линейного CBC drag, фиксированной установки
и предоставленного прогноза. Квадратичный drag и k=1 явно неподдержаны текущим
кодом. IdealPose — идеальная геометрия и искусственное округление для теста,
не реализация Minecraft float/LUT. Фактические transform, phase, ограничения
привода и время запуска ещё требуют игрового адаптера. Spread, столкновения
с промежуточными объектами, чтение bbox/мира и Java-производительность не проверены.
Малая ошибка рекурсионного эталона не является обещанием такой же ошибки в игре.

Ограниченный поиск не гарантирует обнаружение каждого существующего решения,
полный оптимум по времени запуска или обработку всех вырожденностей. Он гарантирует
более узкий контракт: выданный план прошёл описанную проверку модели; недостаток
доказательств/вычислительного бюджета не превращается в разрешение выстрелить.
Сценарии и результаты сохранены в рабочем дереве develop. Новых коммитов и push
при выполнении этой части задачи не делалось.
