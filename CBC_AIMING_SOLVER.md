## Задача и критерий

Найти pitch/yaw для попадания из неподвижной пушки в неподвижную цель, затем — в цель
с известной постоянной скоростью. Основной путь не выполняет потиковую симуляцию:
состояние снаряда для любого заданного тика вычисляется непосредственно по формуле.
Допустимый численный этап — поиск корня по аналитической функции. Это не полностью
замкнутое решение обратной задачи; называть его так нельзя.

Наш вариант ведётся в develop; независимый вариант коллеги — в newcore, в файле
с тем же путём. Пока сравнение с вариантом коллеги не проводилось.

## Предпосылки модели

Свободный полёт, неизменные коэффициенты среды/гравитации, quadratic_drag=false,
нулевой случайный разброс для расчёта центральной траектории. Нет столкновений,
отскоков, пробития и внешнего изменения скорости. Установка и её anchor неподвижны.
Скорость запуска должна определяться по реальному пути fireShot и данным боеприпаса,
а не произвольной константой. Особые снаряды и сторонние модификации требуют проверки.
Основная рекуррентная формула ниже предполагает, что скорость на рассматриваемых
шагах не попадает в область нормализации |v|<1e-4; при k=0 это ограничение не нужно.
Для точной поддержки порога потребуется отдельная аналитическая обработка переходов.

Единицы: положение — блоки, скорость — блоки/тик, ускорение — блоки/тик².
`n` — целое число полностью пройденных шагов; `G=(0,g,0)` — фактическое ускорение
из getForces, обычно с отрицательным g.

## 1. Точная формула прямой задачи

Пусть `d = projectile.drag × density`, а `k = min(d,1)`, `q=1-k`.
Для постоянной среды линейное торможение с ограничением CBC даёт:

```text
a_n     = -k v_n + G
v_(n+1) = q v_n + G
p_(n+1) = p_n + (1-k/2) v_n + G/2
```

Для `0<k≤1` обозначим:

```text
S_n = (1-q^n)/k
A_n = (1-k/2) S_n
B_n = (n-A_n)/k
```

Тогда точное решение рекуррентной модели в вещественной арифметике:

```text
v_n = q^n v_0 + S_n G
p_n = p_0 + A_n v_0 + B_n G
```

Вывод: решение первого линейного уравнения даёт геометрическую сумму S_n.
Суммирование приращений позиции даёт `(1-k/2) Σ v_j + n G/2`.
Подстановка `Σ v_j = S_n v_0 + (n-S_n)G/k` приводит к A_n и B_n выше.

Отдельные точные ветви:

```text
k=0: S_n=n, A_n=n, B_n=n²/2, v_n=v_0+nG.
n=0: S_n=A_n=B_n=0, q^0=1.
k=1, n≥1: S_n=1, A_n=1/2, B_n=n-1/2, v_n=G.
```

Вычисление требует фиксированного числа операций и одного возведения в степень,
без цикла по n. Это утверждение о модели вычислений, не измерение наносекунд/TPS.

Для малых k прямое вычисление `1-q^n` и особенно `n-A_n` теряет точность.
Нужно использовать log1p/expm1 и отдельную устойчивую оценку B_n. Начало ряда:

```text
A_n = n - n² k/2 + n(n-1)(2n-1) k²/12 + ...
B_n = n²/2 - n(n-1)(2n-1) k/12
      + n(n-1)²(n-2) k²/24 + ...
```

Порог переключения и остаток ряда пока не определены. Подстановка k=0 вместо малого k
без оценки пространственной ошибки не считается готовым решением.

## 2. Устранение pitch/yaw из обратной задачи

Для прямого ствола обозначим фиксированный мировой центр вращения C, единичное
направление выстрела u, скорость s и осевое расстояние spawn от C — L.
У стандартного пути CBC при неподвижном anchor геометрия имеет вид:

```text
p_0 = C + L u
v_0 = s u
p_n = C + (L+s A_n)u + B_n G
```

Таким образом, смещение дула учитывается непосредственно, без внешней итерации
«поправить muzzle после изменения углов». Это вывод для проверенного осевого пути
запуска; прочие геометрии требуют отдельного адаптера. L должен быть получен из
фактической сборки и spawn offset CBC; его знак нельзя молча отбросить.

Для цели X(n) кандидат времени удовлетворяет:

```text
R(n) = L+s A_n
D(n) = X(n)-C-B_n G
F(n) = dot(D(n),D(n))-R(n)² = 0
u    = D(n)/R(n)              при R(n)≠0
```

Условие `|u|=1` убирает обе угловые переменные. При R=0 требуется отдельная обработка:
деление запрещено. При R<0 направление восстанавливается с сохранением знака R,
а допустимость такого запуска и ориентации проверяется отдельно.

Для неподвижной цели X(n)=X; для идеального движения с постоянной скоростью W:
`X(n)=X_sample+W(age+delay+n)` в согласованных серверных единицах.
Упреждение входит в ту же функцию; новую историю потиковых позиций строить не нужно.

Направление u преобразуется в желаемые мировые углы, затем в соглашения конкретной
установки CBC с учётом initialOrientation и знаков. Формулы записи полей контроллера
ещё не выведены. Нельзя просто приравнять Minecraft XRot к cannonPitch.

## 3. Что означает численный поиск времени

Замена n на вещественное t в q^n даёт удобное гладкое продолжение формулы для
построения кандидатов. Каждое вычисление F(t) имеет фиксированную стоимость.
Это продолжение точно в целых тиках, но его промежуточные точки не являются
доказанным описанием collision sweep CBC.

Начальная идея: изолировать корни аналитической функции времени, затем уточнять
ограниченным методом Brent либо защищённым Newton. Предыдущее решение можно
использовать как стартовый кандидат при сопровождении, но оно не заменяет поиск
другой ветви при потере текущей.

Нельзя объявлять функцию монотонной, обещать два корня для произвольной движущейся
цели или считать смену знака достаточной для нахождения касательного решения.
Пока нет доказанного глобального изолятора корней, исчерпание бюджета должно
означать «не удалось решить», а не «цель недостижима». Полнота изолятора — следующая
математическая задача; простой перебор времён с шагом 1 тик не принимается.

Сложность при J оценках функции — O(J), а не O(J×длительность полёта).
Нужны пространственный допуск, предел дальности/времени и бюджет J, согласованные
с фактической жизнью снаряда и требованиями механики. Их значения пока не выбраны.

## 4. Аналитическая проверка попадания внутри выбранного тика

В свободном полёте исходный collision segment CBC имеет вид:

```text
H(n,f) = p_n + f v_(n+1),  0≤f≤1.
```

При осевой геометрии:

```text
H(n,f) = C + [R(n)+f s q^(n+1)] u + [B_n+f S_(n+1)] G.
```

Для неподвижной точечной цели в выбранном n условие существования направления
превращается в квадратное уравнение по f:

```text
|X-C-[B_n+f S_(n+1)]G|² = [R(n)+f s q^(n+1)]².
```

То есть выбранный тик можно уточнить алгебраически, без интегрирования предшествующих
тиков. После выбора f направление восстанавливается аналогично разделу 2.
Нужна устойчивая обработка линейного/вырожденного уравнения и его корней в [0,1].

Это ещё не доказательство, что проверки только нескольких соседних тиков около
гладкого кандидата найдут все попадания. Требуется вывести границы такой проверки.
Кроме того, collision segments соседних тиков не обязаны образовывать непрерывную
ломаную: конец p_n+v_(n+1) отличается от p_(n+1) на a_n/2.

Для AABB нужны правила расширения hitbox и пересечения из полного clipAndDamage.
Для движущейся цели надо согласовать фазу измерения и порядок entity ticks: CBC
проверяет доступный ему bbox, а не обязательно bbox цели в момент n+f.
Идеальное непрерывное упреждение нельзя выдавать за точное воспроизведение этого порядка.
Случайный spread ограничивает вероятность попадания даже при точном центральном решении.

## 5. Квадратичный случай

Прочитаны 18 JSON в штатной директории munition_properties/projectiles указанного
коммита: quadratic_drag=true не найден; свойство false либо отсутствует.

При quadratic_drag=true эффективный коэффициент становится
`k_n=min(d |v_n|,1)`. Геометрическая прогрессия с одним постоянным q тогда неприменима.
Наличие дискретного алгоритма обеспечивает возможность численного предсказания, но
потиковый численный прогноз не удовлетворяет основной цели текущей разработки.

Нельзя без доказательства объявлять замкнутое решение невозможным. Пока подхода,
который точно воспроизводит общий квадратичный случай без шагов, здесь не выведено.
Предлагается отдельная ветвь возможностей модели: аналитический линейный путь не
подменяет параметры квадратичного снаряда. При отсутствии специального решателя
такой режим должен быть явно неподдержан, а не молча посчитан как линейный.

## 6. Сравнение начальных направлений

| Подход | Цена прямой оценки | Что пока ограничивает |
| --- | --- | --- |
| Формула дискретного полёта + скалярное время | O(1) на оценку | Нужны изоляция корней и соответствие collision sweep |
| Двумерный перебор pitch/yaw с той же формулой | O(1) на точку, много точек поиска | Лишние неизвестные, узкие решения, полнота сетки |
| Непрерывная формула линейного drag | O(1) | Расхождение с дискретным обновлением CBC |
| Потиковый прогноз для каждой пары углов | O(длительность полёта) на кандидат | Не выполняет основное требование |

Первый подход выбран как основа исследования: он уже даёт точный прямой расчёт
и устраняет две угловые переменные при проверенной геометрии запуска. Сравнение
реальной производительности и готового поведения пока не проводилось.

## 7. Выполненная математическая проверка и следующие шаги

Выполнен отдельный вычислительный расчёт с Decimal precision=70: сравнение формул
для позиции/скорости с исходной рекуррентной моделью. Проверены k=0, 1e-9, 0.01,
0.2, 0.8, 1 и n=0,1,2,10,100,1000 — 36 сочетаний. Максимальное абсолютное
расхождение около 2.25e-54. Это проверка алгебры с высокой точностью; она не доказывает
устойчивость будущего double-кода, корректность интеграции или попадание в игре.
Пошаговый расчёт использовался исключительно как внешний контроль формулы,
не как часть предлагаемого рабочего решателя.

Следующие шаги исследования:

1. Доказать полноту/границы изоляции времени для неподвижной цели и отдельно
   исследовать число ветвей для движущейся цели.
2. Связать гладкие кандидаты с настоящими collision segments, включая касание.
3. Вывести устойчивое вычисление A/B и контролируемые пространственные допуски.
4. Закончить чтение launch/наследования shoot и преобразование направления в углы
   для всех поддерживаемых исходных ориентаций. Учесть lifetime, spread и особые снаряды.
5. Уточнить возраст радарного sample, задержку до выстрела и политику наблюдения.
6. Найти аналитический критерий входа в |v|<1e-4 и обработку этого режима без
   перебора всех шагов. Без этого не обещать точное совпадение на всех допустимых
   боеприпасах, особенно при малой/нулевой гравитации и почти вертикальном выстреле.

ConsumerConnection/LiveResult дают позицию и sampledTick, а не скорость. Для ядра
решателя W пока является входом. Оценка W по наблюдениям — отдельная обязанность
сопровождения; contentVersion не гарантирует свежесть времени, а замороженное
измерение не является очередным наблюдением движения.

Java-код, зависимости и игровые ресурсы не менялись. Игра и Gradle не запускались.
